| A `grep`/`head`/`sed`/`cat`/inline-interpreter read of `.env` or `.env.registry` — or a `docker exec … /app/.env` wrapper around one — is denied with an `[env-read-guard]` reason; or Bash calls are blocked with no guard reason at all (SMI-7157) | The `PreToolUse` Bash guard (`scripts/env-read-guard.mjs`) blocks any command that names a secret-bearing env file as a read target. It inspects the whole command string, so argument order and a `docker exec` wrapper do not evade it. Inspect config state with `varlock load` (default pretty format, masked) or `varlock load --quiet` — **not** `--format json`/`json-full`/`json-full-compact`/`env`, which are unmasked and also denied. `.env.schema` and `.env.example` stay readable; an output-free presence check (`grep -qE '^KEY=' .env`) is explicitly allowed. Genuine false positive: `SKILLSMITH_ENV_READ_GUARD_DISABLE=1` for that invocation, and file a Linear issue so the shape gets added to the allow list. If Bash calls are blocked although they read no secret file, and the block names no `[env-read-guard]` or `[ruflo-host-guard]` reason, suspect a crashed or timed-out guard: `"onFailure": "block"` turns a crash into a block (SMI-7157). Run each guard by hand to see the error: `node scripts/env-read-guard.mjs <<< '{"tool_name":"Bash","tool_input":{"command":"echo hi"}}'`, then the same with `scripts/ruflo-host-guard.mjs`; a working guard prints nothing for that payload and exits 0. Registered in [guards-and-opt-outs.md](../../docs/internal/process/guards-and-opt-outs.md). |
| `gh pr create`, `node scripts/*.mjs`, or a relative `--workspace`/path CLI argument (e.g. `scripts/needle/dispatch.sh`) fails after an earlier `cd` into a worktree or its `docs/internal` submodule (SMI-5978) | `git -C <dir>` does NOT protect these — they read the shell's actual process cwd, not a `git -C` target, so a `cd` left over from a prior command (e.g. `cd docs/internal && gh pr create`) silently redirects them. Check `pwd` before any `gh`/`node`/relative-path command that follows a foreground `cd`, or pass an absolute path. `scripts/needle/dispatch.sh`'s own `--workspace` not-found error now names the cwd it resolved against, to make this self-diagnosing. |
| Scan-coverage alert fired (`scan_coverage_degraded`, SMI-5866) | The security-scan write path has stayed abnormally NULL for skills created in the last 24h — confirm with `SELECT * FROM check_scan_coverage();` via `./scripts/pooler-psql.sh`, then inspect the indexer scan write path (`scripts/indexer/skill-processor.ts` around the `security_score` assignment, and the `validationCache` round-trip in `indexer-runners.ts` — this is the exact class of bug SMI-5849 was). Auto-clears on the first tick back under threshold; re-alerts at most once per 24h while degraded. | `indexer_degraded` alert fired (SMI-6220) | A `Skill Indexer` GitHub Actions run concluded `success` but tripped a threshold arm — the email body names which one(s) (rate-limit bucket, discovery failure-ratio, secondary rate-limit hits, or recheck prevention-outage) with the observed values and thresholds in force. Confirm live with `SELECT * FROM v_indexer_health ORDER BY created_at DESC LIMIT 5;` via `./scripts/pooler-psql.sh`. For a rate-limit arm, check `scripts/indexer/_shared/rate-limit.ts` (per-bucket `*_observed`/`*_remaining_min`); for a ratio/recheck arm, check `scripts/indexer/discovery-orchestrator.phase-split.ts` / `scripts/indexer/recheck.ts`. Disable sending: `SKILLSMITH_INDEXER_DEGRADED_ALERT_DISABLE=1` (repo variable); shadow mode (default, no real send) is controlled by `SKILLSMITH_INDEXER_DEGRADED_ALERT_SHADOW` (unset or non-`'0'` = shadow). Full design: [smi-6220-indexer-alert-threshold-sparc.md](../../docs/internal/implementation/smi-6220-indexer-alert-threshold-sparc.md). |
| `indexer_upsert_blocked` alert fired (SMI-7113) | Supabase's Cloudflare firewall refused one or more skill rows in an indexer upsert. The batch was bisected, so only the refused rows failed; every other row was written. The alert fires on a row not blocked in the last 48h, an exhausted bisect budget, or a truncated block-history lookup, whatever the run's failure ratio. List the refused rows with `SELECT created_at, resource, metadata->>'ray_id' AS ray_id, metadata->>'payload_bytes' AS payload_bytes FROM audit_logs WHERE event_type = 'indexer_upsert_blocked' ORDER BY created_at DESC LIMIT 10;` via `./scripts/pooler-psql.sh`. Use `metadata->'field_lengths'` to find the field that trips the rule. The row's content is never logged, only its identity and sizes. **Scheduled discovery** skips a row blocked in the last 24h, so a repeat offender does not re-alert every slot. **Backfill never skips**: its checkpoint advances past unwritten rows, so a skip would lose them. If the budget was exhausted, the rows past it were not bisected; raise `INDEXER_UPSERT_BLOCK_BISECT_BUDGET` (repo variable, default 64) or wait for the next run. A non-zero exit from the alert step itself means the indexer output was missing, stale or unparseable, which is a different fault from a block. Switches: `SKILLSMITH_INDEXER_UPSERT_BLOCK_ALERT_DISABLE=1` skips only the alert POST; `SKILLSMITH_INDEXER_UPSERT_BISECT_DISABLE=1` (or `true`) restores the old fail-the-whole-batch behaviour and skips the 48h lookup. Registered in [guards-and-opt-outs.md](../../docs/internal/process/guards-and-opt-outs.md). [Details](../../docs/internal/implementation/smi-7112-indexer-ops-reliability-sparc.md) |
| `indexer_lock_starvation` alert fired (SMI-6209) | Arm A (last 3 indexer runs all lock-skipped) or Arm B (a run_type's last non-skip row is stale beyond its threshold — 12h discovery, ~30h maintenance/recheck) tripped — the email body names which arm(s) and, for Arm B, the exact staleness/threshold per run_type. Confirm live with `SELECT id, created_at, metadata->>'run_type' AS run_type, metadata->'meta'->>'status' AS status FROM audit_logs WHERE event_type = 'indexer:run' ORDER BY created_at DESC LIMIT 10;` via `./scripts/pooler-psql.sh`. Remediation: (1) identify the offending `indexer-backfill.yml` run holding the singleton lock — `gh run list --workflow=indexer-backfill.yml --status=in_progress` and note its dispatch/run ID; (2) either cancel it (`gh run cancel <run-id>`) or wait for its SMI-5311 heartbeat to stop and the 20-min stale-lock TTL to lapse; (3) confirm the lock actually released with `SELECT locked_at FROM indexer_lock WHERE id = 1;` — `locked_at` should be NULL or older than 20 minutes. Re-alerts at most once per 24h while degraded; auto-clears on the first tick with neither arm tripped. Disable sending: `SKILLSMITH_INDEXER_LOCK_STARVATION_ALERT_DISABLE=1`; shadow mode (default, no real send) is controlled by `SKILLSMITH_INDEXER_LOCK_STARVATION_ALERT_SHADOW` (unset or non-`'0'` = shadow). Root cause (unbounded `indexer-backfill.yml` lock-hold) fixed by SMI-6246 — see the next row; this alert should now be rare. |

| `refresh_unhealthy` alert fired (SMI-7114) | The refresh observer (`scripts/ci/refresh-observer.sh`, run by the `refresh-metadata.yml` schedule every 4h) found at least one arm tripped; the email names each: `stale` (no non-failed `refresh:run` in 9h), `dispatch_stale` (no pg_cron `refresh:dispatch` row in 9h: the dispatcher has not completed an enqueue.
