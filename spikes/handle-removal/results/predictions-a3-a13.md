# Predictions for A3/A4/A7/A8/A9/A10/A11/A12/A13 against V0/V1/V2, written before running

Written before any of these attacks were built or run against VR. Basis:
VR's three structural properties established in checkpoints 2-4 --
(1) a directory's fd is pinned the moment it's opened, so a later NAME-based
swap can't affect what's already held; (2) V1/V2 compare (dev,ino) at
removal time against what the guard pass recorded; (3) only V2 re-verifies
file CONTENT (hash) before quarantining; V0/V1 never read file content nor
any timestamp field at all.

| Attack | Prediction | Reasoning |
|---|---|---|
| A3 (swap before the walk ever touches the entry, via rename-aside) | **FAILS under guard=none (all of V0/V1/V2); PASSES under guard=hash.** Same shape as the already-confirmed A6/inner/none residual | The swap happens before VR's guard pass has ever observed the name, so there is no earlier identity to compare against -- structurally identical timing to A6/inner |
| A4 (swap after the entry is already opened+held, before its own content is touched) | **PASSES cleanly, all of V0/V1/V2, guard irrelevant** | Same timing regime as A5 (already 0/300 loss): the fd is already pinned before the swap, so V0 walks through the OLD held fd regardless of what the name now points to, and V1/V2's identity check would also catch a mismatch if V0's fd-only protection weren't already sufficient |
| A7 (file substituted, same-tick, racing inode reuse) | **V0 FAILS (deletes the substitute). V1 FAILS when reuse is achieved (dev,ino matches, content doesn't -- V1 never reads content). V2 PASSES (0 bytes lost, `entry-changed` stop) whenever reuse is achieved.** This is the plan's own stated expectation for V0 *and* V1 -- only V2 is supposed to survive it, which is the whole point of V2's content re-hash | Must be built with the SAME same-tick delete-recreate technique as A5, not a simple substitution -- a simple (non-racing) substitution would get a fresh inode and V1 would trivially catch it via identity alone, which would not actually test what A7 exists to test |
| A8(a) dir replaced by a symlink to an outside dir, before descent | **PASSES, all of V0/V1/V2, 0 outside bytes touched** | `openAt`'s `O_NOFOLLOW` (baked into the shim, used identically by every VR variant) refuses to open a symlink as a directory regardless of variant -- this is not an identity-check property, it's a no-follow property every variant inherits from C1 |
| A8(b) symlink replaced by a directory with user files, after the guard pass already recorded it as a symlink | **PASSES for V1/V2** (identity/type mismatch at removal time stops it). **V0's outcome is uncertain and is the one prediction I'm not confident calling** -- V0 has no explicit type check, but my implementation unlinks a recorded-symlink via `unlinkAt(D, name, isDir=false)`; calling that on what is now a real directory should fail with EISDIR as an unplanned side effect of the record-driven `isDir` flag, not by design. Flagging this now so a V0 pass here isn't mistaken for intentional protection |
| A9(b) APFS-cloned birthtime (`setattrlist ATTR_CMN_CRTIME`) on a same-tick, non-reused-inode replacement | **PASSES, all of V0/V1/V2, and "no timestamp field read" holds trivially** -- `statAt`'s C implementation never copies any time field into the JS-facing result, and no VR code path ever requests one. This attack exists to defeat a *clock gate*; VR has no clock gate to defeat, so it should be structurally inert against VR regardless of how convincingly the clone is forged | This is the attack I most expect to just confirm a structural property rather than reveal anything new -- worth running anyway since "expect to confirm" is still a checkable claim, not an excuse to skip it |
| A10(a) whole tree replaced before bind (even earlier than A6/root's own hook, which fires just after bind) | **FAILS under guard=none; PASSES under guard=hash.** Same shape as A6/root/none vs guardHash, because before `beforeBind` fires, nothing is pinned yet -- there is no fd to protect anything | Genuinely expect this to be redundant with A6/root's own finding, just one hook point earlier; worth confirming the earlier hook doesn't change the outcome, since if it did that would itself be a finding |
| A10(b) identical serialization + a hard link to an outside file | **PASSES trivially, all variants, guard=hash allows removal, the outside file survives regardless** | `unlinkAt` removes one name, not the underlying inode's data, while any other link to it exists -- this is a property of `unlink(2)`, not of VR's identity logic |
| A11 hard link inside the tree to an outside file (no attack, property check) | **PASSES trivially, all variants** | Same `unlink(2)` property as A10(b), with no swap involved at all |
| A12 injected EBUSY (inner rmdir) / EACCES (unlink) mid-walk | **PASSES, all variants** -- stops with the injected errno, path, and entry; nothing removed after it | UD20's stop-on-first-error behavior is in the *shared* removal-walk skeleton (`walk.mjs`'s `stop()` helper), not gated behind any per-variant identity/content check, so I don't expect this to differentiate V0/V1/V2 at all |
| A13 concurrent racer: a real second process loops A3/A5/A7/A8-shaped mutations against 300 real walks | **V0 shows losses (from the A7-shaped substitution racing, same as A7 alone). V1 shows losses too, for the same reason (A7 defeats V1 specifically). V2 stays at or near 0 loss.** The one attack I expect the *rate*, not just the pass/fail shape, to differ from the single-attack versions, since real concurrency adds timing variance a synchronous hook can't reproduce | This is the prediction I hold least confidently -- real OS-level concurrency (a second live process) behaves differently from a synchronous in-process hook, and I have not previously measured how much |

**What I'm most confident about:** A4, A10(b), A11, A12 (near-certain PASS, low information value, but the plan's own criterion 1 requires them regardless).
**What I'm least confident about:** A8(b)'s V0 behavior (uncertain, flagged above) and A13's exact loss rate (real concurrency, unmeasured territory).
**Where I expect the interesting finding:** A7, because it's specifically designed to separate V1 from V2, and if V1 does NOT fail it would mean my same-tick reuse technique didn't work as intended for a *file* the way it did for a *directory* in A5/A6 -- that would itself be worth reporting plainly rather than declaring victory.
